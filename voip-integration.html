Context & Diagnosis

Acme Services is a 25-person sales team using a VoIP provider for calls (and SMS with some clients), Salesforce as CRM, and Slack internally. The VoIP provider already syncs call data into Salesforce — calls are logged and visible — but the sync is passive: it records that a call happened and nothing acts on that information afterward.

The trigger for this engagement was a specific incident: a VIP client's call went to voicemail, no one followed up for two days, and the client raised it directly with Acme's CEO. That single event is what the entire system below exists to prevent from happening again.

Deliverable 03

Architecture — Request Flow & Data Model

Request Flow — One Webhook, Four Outcomes
1
POST /webhooks/voip

Inbound call event received from the VoIP provider

2
Claim the event id idempotency

Insert a placeholder row; a unique constraint rejects duplicate deliveries — already-claimed events return already_processed: true and re-run nothing

3
Normalize the phone number → E.164

One shared function, applied at the earliest possible point — the exact bug class caught in the incident below

4
Match against customers one query

Four direct outcomes: VIP missed, non-VIP/completed, existing lead, unknown number

5
Branch & act

VIP missed → CRM task + Slack @-mention (fallback channel if no owner) · Unknown → create lead + notify sales · Everything else → record only

6
Retry, then fail visibly

Downstream CRM/Slack calls retry with exponential backoff (tenacity); exhausted retries write a queryable failed_events row, never a silent drop

Data Model
TablePurposeKey Constraint
customersCRM contact — a lead is just a row with source = 'inbound_lead'phone_number unique (dedup)
callsOne row per call event actually processedvoip_event_id unique (idempotency)
failed_eventsExists only when retries are exhausted — queryable, not just loggedFK → calls.id
Two Distinct Guards — Deliberately Not Conflated
Guard 01
Event idempotency
  • Unique constraint on calls.voip_event_id — stops the same webhook delivery being processed twice
Guard 02
Lead deduplication
  • Unique constraint on customers.phone_number — stops the same caller becoming two leads, even under a race

Both rely on a database constraint as the source of truth, not application-level locking — the service may run as more than one process.

Deliverable 05

Incident — Caught Before It Shipped

HIGH severity — during pre-launch UAT, a bug reproduced the exact business failure this project was built to prevent: a VIP customer's missed call silently going unfollowed-up.
Timeline
TimeEvent
18:40Full suite green — 20/20, all against app-generated test data
18:52UAT started with data shaped like a real CRM export (national-format numbers)
18:53Reproduction test written to target the suspected gap
18:54Confirmed failing — VIP call misclassified as a new lead
19:00Fix implemented and verified
19:0221/21 passing, including the new test
Root Cause

Every comparison assumed both sides were already E.164-normalized. That held for any customer created through the app — but nothing enforced it for a row written any other way, such as a bulk CRM import landing numbers in national format. A design gap in enforcement, not in the design itself: the architecture doc already required this invariant — it just wasn't guaranteed at every write path.

Reproduction → Fix → Verify
$ pytest tests/test_incident_phone_format.py -v FAILED ...::test_legacy_national_format_seed_data_is_still_matched AssertionError: expected the call to match the existing VIP customer and trigger follow-up, but got branch_taken='new_lead' assert 'new_lead' == 'vip_missed'
# app/models.py — the fix: enforce the invariant # on the model itself, not at every call site @validates("phone_number") def _normalize_phone_number(self, key, value): return normalize_phone_number(value)
$ pytest tests/ -v ...::test_legacy_national_format_seed_data_is_still_matched PASSED ======================== 21 passed in 2.18s ========================
Why it was caught: the existing 20-test suite passed the whole time — every one of those tests created its fixtures through the app's own normalized code path. The gap was in test data realism, not test coverage: seeding data shaped like a real import, instead of only data shaped like the app's own writes, is what surfaced it.
Deliverable 06

Translating the Incident for a Non-Technical Stakeholder

The same incident above, rewritten for Sam (the client's Ops Manager) — no jargon, no code, same facts, framed around what it means for them.

What happened: a testing update on the missed-call alerts

For Sam — no technical background needed to read this.

While testing the new system before launch, we found — and already fixed — a bug that could have caused the exact problem this project was built to prevent: a VIP client's missed call not triggering an alert. It never affected a real client, because we caught it during our own pre-launch testing, using practice data, before the system went live.

Your team enters phone numbers the normal, human way — like 06 12 34 56 78. The VoIP provider uses the international format instead — like +33 6 12 34 56 78. Same number, two different-looking versions of it. We'd already handled that difference for incoming calls — what we'd missed was a one-time import scenario landing a number in the "wrong" format.

We changed the system so that any phone number it stores — no matter how it got there — automatically converts to one consistent format the moment it's saved. Nothing you need to do right now.
